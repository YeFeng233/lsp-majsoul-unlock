# 三麻 Mortal 推荐质量验证

2026-10-24：三麻已接入本地 Rust SP 算法。以下固定测试组的 **775×34 完整输入、44 动作合法集合和首选推荐全部与独立参考一致**。仍保持实验性：这些结果验证模型接入的一致性，不代表实战胜率、最优出牌或所有游戏状态均已覆盖。

## 方法与来源

同一份用户模型分别接收生产编码和独立参考编码，在电脑本地使用同一网络推理，比较完整输入、合法集合及贪心首选。参考为 [Akagi 固定提交的 libriichi3p](https://github.com/shinkuan/Akagi/tree/91cc2993e4e3682248d33d73d93afe055040e700/mjai_bot/mortal3p) Windows/Python 3.12 二进制和同提交的 model.py，均校验固定 SHA-256。模型及参考二进制均不分发，也未上传用户权重。

实际协议为 775×34 / 44，碰=38、杠=39、拔北=40；其他三麻分支须单独核对。参考 Bot 把选杠牌子任务放在主动作前面，工具比较主动作批次。精简检查点 SHA-256 为 `03859386c2fc300c2a03b26613f0e8e62e70d5632336dd5a64e8ab726c5d92c8`，与原始文件的 844 个推理张量完全相同。

SP 算法选取 [Mateces/mortal-sanma 固定提交](https://github.com/Mateces/mortal-sanma/tree/bf69bc320d6072bbeae2abfdc57bf876a5bab2e3/libriichi/src/algo) 的纯 Rust 部分，包含向听、和牌计分、有限巡数进张和期望值计算。代码、查表数据、许可证及原文件哈希保留在 `external/mortal-sp`；不依赖 Python 或参考二进制，全部在本机计算，相同输入复用缓存。

## 结果

下表为**参考首选动作一致数**，不是推荐正确率或胜率。前一轮 e84823f 的结果作为对照。

| 测试组 | 前一轮首选一致 | 本轮首选一致 | 本轮完整输入一致 | 本轮合法集合一致 |
| --- | --- | --- | --- | --- |
| 开发集：120 个生成局面 + 9 个专项 | 120/129 | 129/129 | 129/129 | 129/129 |
| 留出集：种子 20261026，300 个生成局面 + 9 个专项 | 290/309 | 309/309 | 309/309 | 309/309 |
| 新留出集：种子 20261027，180 个生成局面 + 9 个专项 | 未测 | 189/189 | 189/189 | 189/189 |
| 3 份公开三麻牌谱的无鸣牌前缀 | 69/70 | 70/70 | 70/70 | 70/70 |
| 扩展专项与完整回归集 | 未测 | 43/43 | 43/43 | 43/43 |
| 手机上 ARM64 生产编码，同一扩展集 | 未测 | 43/43 | 43/43 | 43/43 |

逐项误差阈值为 1e-6。Android 行使用手机实际导出的生产向量，随后在电脑用同一模型对比首选；没有向游戏发送操作，也不等同于在手机上跑完 43 场对局。

扩展集覆盖拔北后补牌、对手拔北、碰后立即弃牌、暗杠/明杠/加杠后的补牌、对手碰、立直宣言后的弃牌、一发自摸、拔北补牌自摸、牌墙耗尽、不同分数顺序与座位轮转，并复用部分核心案例。三组生成测试也复用了相同的 9 个专项，不能把各行相加视为独立对局数。公开样本来自 3 场牌谱，仅保留每局首次鸣牌或拔北之前的决策，隐藏对手手牌及摸牌；样本相关，是否属于模型训练数据未知。

手机 43 个局面首轮编码中位数约 **0.09 ms**、最大 **104.55 ms**；紧接着重复编码中位数约 **0.07 ms**、最大 **0.37 ms**。首轮可能包含跨案例缓存命中及首次查表初始化；耗时仅含特征编码，不含网络推理、通信和操作延迟，不代表其他手机的性能。

本轮结果见 [SP 机器报告](validation/mortal-sanma-sp-20261024.json)；前一阶段的失败案例及公开牌谱来源/哈希保留在 [历史报告](validation/mortal-sanma-quality-20261024.json)。43 个完整向量已固化为 Rust 回归，CI 检查不需要权重或 Python。

## 本轮修复

- 补齐 652–774 通道的本地 SP 输入，按有效牌张张数选取最佳进张，保持参考的巡数、概率及期望值归一化规则。
- 修正 1 万/9 万宝牌指示关系。保留旧参考在里宝牌估算、排名及碰牌占位中的历史编码行为，以匹配已有模型；这些兼容处理不修改游戏分数、排名或规则。
- 从当前局事件重建宝牌河牌、手切和立直弃牌标记；追加宝牌前已打出的牌保留其原始标记。
- 使用匹配的向听算法及有役、存活等待、振听条件生成弃牌质量；立直接受后保持宣言时的质量特征，碰后保留原等待状态。
- 修正未知手牌时对手拔北漏记可见北牌；补齐和牌回退中的天和/地和、一发、双立直、岭上及拔北奖励计分。

原生 79 项回归、SP 算法 11 项检查及协议恢复 13 项检查通过；另有 2 个上游四麻计分夹具保持原有忽略状态。ARM64 APK 编译、签名、依赖及页对齐检查通过，已覆盖安装到测试手机。Android 39 项控制器、四麻/三麻 ONNX/JNI 及原有两个 Mortal 模型加载推理自检通过；模型选择、无人值守和悬浮窗设置均已核对保留。

## 限制

尚未完成所有完整牌谱、抢杠/抢北、特殊规则及多杠选择、立直后具体弃牌等全部二阶段动作的端到端对照，也没有成组长局对战基准。本轮针对该 775 通道三麻合同；四麻 Mortal 仍有部分近似特征。

SP 提供模型所需输入。悬浮窗其他分析指标仍由原来的分析模块产生，本次没有将它们改成模型校准后的实战概率。

## 复现

需 Windows/Python 3.12、CPU PyTorch、NumPy、requests；解析公开 XML.zst 另需 zstandard。参考目录中保存上述固定提交的 libriichi3p.pyd 和三麻网络定义 reference_model.py，自行提供检查点。

```powershell
cargo build --release --locked --manifest-path external/Akagi/native_bot/Cargo.toml --example mortal_observation_replay
python tools/validate_mortal_sanma.py --reference-dir <参考目录> --checkpoint <模型.pth> --replay-exe <mortal_observation_replay.exe> --output <结果目录> --samples 300 --seed 20261026
python tools/mortal_sanma_extended_cases.py <cases.json>
python tools/validate_mortal_sanma.py --reference-dir <参考目录> --checkpoint <模型.pth> --replay-exe <mortal_observation_replay.exe> --output <结果目录> --cases <cases.json>
```

手机使用同一 Rust 示例的 Android 构建导出生产向量，再用 `--production-observations <导出.json>` 替代 `--replay-exe` 比较；案例顺序和 ID 必须一致。`--export-fixtures <路径>` 可导出最多 64 个不含权重的完整参考向量。公开牌谱前缀由 tools/tenhou_sanma_prefix_cases.py 生成。
