# 雀魂 Max Hook 独立管理界面设计

日期：2026-09-22　状态：实施中（P1 管理应用外壳已完成）

本方案以现有 `hook-probe` 为基础，设计一个独立发布的 Hook 模块管理应用，使用用户提供的麻将牌图标，提供运行概览、日志查看、检查更新三个页面。新应用将迁入新仓库，独立构建和发布，与当前仓库的代理应用 `app/`（`com.yefeng.majmax`）是两个产品。管理界面与 API 102 Hook 模块打包在同一个新应用 APK 中，用户只需安装这一份 APK。

工作名称为“雀魂 Max Hook”；原型包名 `com.yefeng.majmax.hookprobe` 暂作为兼容基线，正式发布前确定最终 applicationId。独立发布不要求更换现有 Hook 包名；若更换，需按全新模块安装并重新配置 LSPosed 作用域。MOD 功能配置继续由游戏内“设置 → MOD设置”承载，包括同一昵称弹窗中的确认与“恢复原昵称”。

已确认的发布决策：**新应用、新仓库、独立版本与签名；更新检查指向未来提供的新仓库地址。** 新仓库尚未指定不阻碍界面与更新逻辑开发，开发构建以“尚未配置更新源”呈现，不向旧仓库发出替代请求。

本轮已将 P1 管理应用外壳接入 `hook-probe`：桌面入口、图标、主题、概览/日志/更新三页、管理侧日志筛选，以及新仓库未配置空态均已实现并通过 `assembleDebug`。游戏侧结构化诊断文件、root 只读适配器和正式新仓库发布仍按下文计划推进；示例版本与状态不代表已经发布或真机实测。

## 1. 现状与设计依据

| 已核实的仓库现状 | 对设计的影响 |
| --- | --- |
| `hook-probe/build.gradle.kts`：0.4.3 / versionCode 7，Android 10 起，ARM64，API 102 | 以此为新应用原型；若沿用包身份与签名，升级保留现有模块身份 |
| `hook-probe/src/main/AndroidManifest.xml`：没有 Activity、桌面图标和网络权限 | 需要新增 Launcher Activity、图标、主题和检查更新所需的 INTERNET 权限 |
| `ProbeModule.java` 在游戏进程初始化；入口日志写入 LSPosed 模块日志 | 管理界面自己的进程不能据此直接判断模块是否已在游戏内生效 |
| C++、Rust、Lua 桥接日志主要使用 `MajsoulHook` logcat 标签 | 需要设计跨应用日志读取和持久化；仅在管理应用执行普通 logcat 不足以完成需求 |

| 原 `app/` 是不同包名的代理应用，已有 Compose 日志界面 | 仅可借鉴组件与交互，不依赖旧应用安装、配置或发布 |
| `.github/workflows/build.yml` 发布旧代理应用 | 新应用在新仓库独立建立 CI；旧仓库的 release 不作为更新源 |

源码入口：[模块说明](../hook-probe/README.md)、[Java 入口](../hook-probe/src/main/java/com/yefeng/majmax/hookprobe/ProbeModule.java)、[原生 Hook](../hook-probe/src/main/cpp/probe.cpp)、[Rust 入口](../hook-probe/rust-modder/src/lib.rs)、[现有发布流程](../.github/workflows/build.yml)。

## 2. 产品结构

采用三个带文字的底部导航项，默认进入概览；切换保留日志筛选条件和滚动位置。

| 页面 | 核心问题 | 主要操作 |
| --- | --- | --- |
| 概览 | 装了哪个版本，最近运行是否正常？ | 打开雀魂、刷新诊断、查看异常日志 |
| 日志 | 哪一步发生了什么？ | 搜索、筛选、暂停跟随、复制、导出 |
| 更新 | 有没有可用的 Hook 模块新版？ | 检查更新、阅读说明、打开对应发布页 |

“关于”放入右上角菜单：版本、仓库、上游、开源许可、主题设置。首页保留一句“MOD 选项请在游戏内设置中调整”，点击展开路径说明；首版不承诺直接跳转至 Unity 游戏设置窗口。

管理应用使用 Android 原生界面体系，游戏内设置页继续使用游戏组件。两者通过品牌配色和命名关联，各自适配竖屏系统操作与横屏游戏操作。

### 3.1 图标资产

- 原件：`docs/assets/majsoul-max-icon-source.png`，1254 × 1254 PNG，原样复制。
- SHA-256：`5691BE0735DE73E517A2D5157E784E367DCA812BF8B1226A345D494897BA7762`。

- Android 要求 adaptive icon 图层为 108 × 108 dp，关键标识置于内部安全区域；需检查圆形、圆角方形等蒙版中的牌面完整性。[Android 自适应图标规范](https://developer.android.com/develop/ui/views/launch/icon_design_adaptive)
- 深色模式仍沿用原图。单色主题图标作为后续可选资产，需单独制作可辨识的轮廓与镂空，不直接把整张不透明 PNG 当作 monochrome 层。

管理应用原型已使用该原件作为桌面、系统应用信息和页面品牌图标；这里保存的文件仍是后续 adaptive icon 图层制作的唯一原件。

### 3.2 界面风格

使用 Material 3 组件，绿色作为操作色，米白作为主背景，借用麻将牌的圆角与留白。避免大面积贴图和装饰遮挡日志。首版默认保持品牌配色，不启用动态壁纸取色。

下表是设计色值，不宣称为原图逐像素取色结果。

| Token | 浅色 | 深色 | 用途 |
| --- | --- | --- | --- |
| Primary | `#007A46` | `#78D8A4` | 主按钮、选中导航、链接 |
| OnPrimary | `#FFFFFF` | `#003920` | 主按钮文字 |
| Background | `#F7F7EF` | `#101813` | 页面背景 |
| Surface | `#FFFEF8` | `#1B261F` | 卡片、底部导航 |

| Error | `#B42332` | `#FFB3B7` | 失败状态 |

- 页面边距 20 dp，卡片内边距 16 dp，区域间距 16–24 dp；卡片圆角 20 dp，输入框及筛选容器 12 dp。
- 标题 24 sp，卡片标题 18 sp，正文 14–16 sp，辅助文字 12 sp；日志正文 12–13 sp 等宽，中文使用系统回退字体。
- 点击区域至少 48 dp；状态同时使用图标、文字和颜色。图标按钮提供 TalkBack 描述，装饰性品牌图不重复朗读标题。

- 字体放大时允许按钮换行和卡片增高，重要状态及操作不能依赖截断文本。动态数字不触发整页跳动。

“最近运行”是对诊断证据的描述，不等价于“当前已启用”。首版不读取 LSPosed 私有数据库、不通过管理器是否安装推断作用域，也不以单次旧日志显示永久绿色“运行中”。

| 情况 | 主文案 | 操作与规则 |
| --- | --- | --- |
| 尚未授权诊断读取 | 尚未读取游戏运行记录 | 提供“读取诊断”；首次点击说明用途后由设备 root 管理器授权 |
| 未安装目标游戏 | 未检测到雀魂 | 禁用打开游戏；日志和更新仍可使用 |
| 已授权但没有诊断文件 | 暂无游戏运行记录 | 引导在 LSPosed 启用模块、选择游戏作用域并启动游戏；不能断言未启用 |
| 本次会话正在初始化 | 最近记录：模块初始化中 | 显示时间与已完成阶段 |
| 有完整成功事件 | 最近一次初始化成功 | 展示模块版本、游戏版本及记录时间，不保证当前游戏进程仍存活 |
| 有明确失败事件 | 最近一次初始化失败 | 显示简短原因，“查看日志”带入对应会话和错误筛选 |
| 安装版本与游戏记录版本不同 | 新版本将在重启游戏后载入 | 分别显示“已安装”和“游戏最近载入”版本，不自动强停游戏 |
| 只有历史缓存／读取失败 | 显示上次记录 | 同时标注最后读取时间和当前读取错误，不伪装成新结果 |

“打开雀魂”通过 PackageManager 获取目标游戏的启动 Intent；失败时提供系统应用信息入口。Manifest 仅声明目标包的可见性查询。应用首开不自动请求 root；用户已授权后，概览恢复前台可读取一次状态快照，点击刷新才主动重读。

### 4.2 日志

~~~text
┌──────────────────────────────────┐
│ 日志                  [导出]  ⋮  │
│ [游戏模块]  [管理应用]             │
│ [搜索消息或事件                  ]│
│ [全部级别 ▾] [来源 ▾] [会话 ▾]    │
│ 最近会话 · 14:32     跟随中 [暂停]│
│ ──────────────────────────────── │
│ 14:32:01  信息  入口               │
│ 模块已载入                        │
│ 14:32:02  信息  Modder             │
│ 消息处理核心初始化完成             │
│ 14:32:03  信息  游戏界面           │
│ MOD 设置页注入完成                │
│                                  │
│               [回到最新 · +12]    │
│    ○ 概览     ≡ 日志     ↓ 更新   │
└──────────────────────────────────┘
~~~

- 默认“游戏模块”，展示最近会话已有的 INFO/WARN/ERROR；“管理应用”展示更新、诊断读取及界面错误，无需 root。
- 来源可选入口、Native、Rust、游戏 UI；来源与级别是结构化字段，不按日志文字包含 `ERROR` 判断。
- 默认换行；时间与级别为一行元信息，消息在下一行。点击展开完整详情，提供复制单条；技术事件名、线程与进程号收进详情。
- 搜索作用于当前加载范围，输入防抖 250 ms；标注“已载入最近 N 条”，不暗示搜索覆盖已被轮转删除的历史。
- 向上滚动自动停止跟随；新增日志只更新“回到最新”计数，不抢走滚动位置。“暂停”冻结页面快照；恢复后从最近游标补读，丢失区间明确标注。
- 旋转屏幕、切换页签保留来源、筛选、查询和滚动位置。只有日志页在前台且未暂停时每秒最多刷新一次；退到后台即停止读取。
- 导出前选择“当前筛选结果”或“已载入会话”，展示条数；生成脱敏 TXT 或 JSONL，并通过系统分享面板交给用户选择目标。
- 分享文件只放在管理应用 `cache/exports/`，使用非导出的 FileProvider 和临时 URI 读取授权；不直接分享游戏私有路径。[Android 文件分享文档](https://developer.android.com/training/secure-file-sharing/share-file)
- 菜单提供“清除本机缓存”，确认文案说明仅清除管理应用缓存和导出文件，后续刷新可能重新读取游戏记录；首版不提供删除游戏源日志的 root 写操作。
- 未授权、拒绝授权、文件为空、过滤后无结果、文件损坏、读取超时分别给出对应空态，不全部显示“暂无日志”。拒绝后不重复弹授权，只有用户再次点击才重试。

## 5. 日志与状态的数据方案

### 5.1 首版选择：游戏侧限量持久化，管理侧 root 只读

Android 应用私有文件默认隔离；模块被注入游戏后写入的文件属于游戏 UID，管理应用不能因二者代码来自同一个 APK 就直接读取。[Android 应用专属存储文档](https://developer.android.com/training/data-storage/app-specific)

针对现有已 root 设备，首版采用**模块在游戏进程写入有界诊断文件，管理应用经用户授权后只读指定文件**。这样打开管理界面前的初始化过程也能保留，不依赖一直打开日志页或无线调试。

不把系统 logcat 缓冲区作为唯一历史来源；现有 LSPosed/logcat 日志继续用于早期失败的辅助排查。后续若要免除管理应用 root 授权，再单独验证 libxposed 服务或受限 IPC 的兼容性，不把未经验证的跨 UID 服务当作现成功能。

~~~mermaid
flowchart LR
    A[游戏内 API 102 入口] --> B[Java 入口诊断队列]
    C[Native / Rust / Lua] --> D[核心诊断队列]
    B --> E[游戏私有目录：有界日志]
    D --> E
    D --> F[状态快照]
    E --> G[受限 root 只读适配器]
    F --> G
    G --> H[管理应用缓存与 ViewModel]
    H --> I[概览 / 日志]
    J[GitHub Hook Releases] --> K[更新仓库]
    K --> L[更新页]
~~~

新增诊断目录位于现有模块目录下：

~~~text
<游戏 filesDir>/majsoulmax-hook/diagnostics/
  entry.jsonl       Java 入口日志
  entry.1.jsonl     入口轮转文件
  core.jsonl        Native / Rust / Lua 汇总日志
  core.1.jsonl      核心轮转文件
  status.json      最近会话状态快照
~~~

写入端使用 `Context.getFilesDir()`；读取端限定当前 Android 用户、固定目标包、固定 diagnostics 目录及上述文件白名单。当前设备对应 `/data/user/0/com.soulgamechst.majsoul/files/majsoulmax-hook/diagnostics/`，实现不能将用户编号 0 当作所有设备的常量。首版不跨工作资料或其他用户读取。

### 5.2 采集与性能约束

- Java 入口日志由一个 Java 写入线程负责；Native、Rust、Lua 统一进入一个核心诊断 sink，每个日志族仅一个写者，避免多个语言同时轮转同一文件。
- 初始化诊断必须先于 Rust 配置调用，以便记录原生库加载或配置失败。获得游戏 Context 之前先保留至多 128 条入口事件；若连 Activity 入口都失效而无法落盘，概览显示无记录，引导查看 LSPosed 入口日志，不编造失败原因。
- 核心 sink 通过独立诊断 C ABI 初始化；C++ 回调在初始化前缓冲少量事件，Rust 内部直接使用同一队列。桥接只传事件内容，不借日志通道写配置。
- Hook、游戏主线程和网络回调只做有界入队；不等待文件写入、root、网络、管理应用或锁竞争。队列满时优先丢弃低级别事件，记录聚合丢弃计数。
- 默认持久化 INFO/WARN/ERROR。高频逐包替换信息降为 DEBUG，或聚合为每 5 秒的收发处理计数；不持久化 Liqi 正文、账号、昵称、Token、完整 URL 或用户输入。
- 每个日志文件上限 1 MiB，两个日志族共最多 4 MiB；单条上限 8 KiB；核心队列上限 512 条且总量不超过 512 KiB，先触达任一上限即限流。
- 正常情况下每秒批量刷新；错误触发后台尽快刷新，但不在游戏线程同步 fsync。突发崩溃可能损失最后一批日志，界面不能声称这是完整崩溃报告。
- 磁盘满、目录不可写或诊断异常时停用文件 sink，保留现有消息原样放行策略；禁止诊断错误递归记录自身。
- 管理应用每页最多保留 2,000 条、4 MiB 解码后数据；缓存总量不超过 4 MiB，导出缓存总量不超过 8 MiB，超过 24 小时的导出文件在下次启动时清理。

### 5.3 数据协议与读取一致性

JSONL 每条至少包含以下字段，详情缺省时允许省略：

~~~json
{
  "schemaVersion": 1,
  "sessionId": "per-process-random-id",
  "writer": "core",
  "seq": 42,
  "timestampMs": 0,
  "elapsedMs": 12345,
  "pid": 1234,
  "level": "INFO",
  "source": "rust",
  "event": "modder.ready",
  "message": "消息处理核心初始化完成"
}
~~~

示例时间占位值不是有效运行记录。会话 ID 在入口生成并传入原生，两个写者各自递增 seq；以 `(sessionId, writer, seq)` 去重，同会话按单调时间排序，墙上时间只用于展示。

`status.json` 包含协议版本、会话、记录时间、游戏版本、实际载入的模块 versionCode/versionName、初始化阶段、Rust/send-hook/receive-hook/UI 各项结果及有限的错误码。由核心单写者临时文件写入后原子替换；核心未启动时通过 entry 事件呈现入口失败。UI 就绪是独立状态，不能掩盖消息 Hook 尚未就绪。

读取按文件标识和偏移增量处理，轮转时重读有限尾部再去重；忽略尚未写完的最后一行，下次补齐；损坏行计数后跳过。未知 schema 显示“不支持该诊断格式”，保留缓存，不误判模块故障。日志或快照缺失都不等于模块关闭。

root 适配器只接受内部文件枚举和有界数字偏移，不接受自由命令或来自 UI/远端的路径；验证规范路径、普通文件及所有者，不跟随指向目录外的符号链接。传回数据有长度上限，stdout/stderr 有界消费，固定读操作超时后关闭子进程。授权等待单独显示“等待授权”，取消或超时不反复唤起授权框。

读取会话随前台诊断操作创建和关闭，禁止常驻 root 守护进程。root 被拒绝、撤销或 SELinux 阻止读取时显示具体读取状态；更新页和管理应用自身日志仍然可用。

## 6. 更新协议与发布配套

### 6.1 来源和识别

更新来源是用户后续指定的**新 Hook 仓库**。构建配置通过 `-PupdateOwner`、`-PupdateRepo` 与 `-PupdateChannel` 生成 `UPDATE_OWNER`、`UPDATE_REPO` 和 `UPDATE_CHANNEL`，由仓库地址解析为 GitHub owner/repo；业务代码不写死当前 origin。开发阶段未配置时进入独立空态，不发网络请求；正式 release 构建要求填写有效的新仓库配置。应用不提供让最终用户输入任意更新服务器的入口。

检查对象是新应用 APK，不能拿上游 Rust 的 `0.7.0` 或旧代理应用版本与 Hook 版本比较。更新源变更与最终 applicationId 同时固化进发布配置；包名校验从本应用身份读取，不依赖原型包名常量。

拟使用新仓库的 GitHub 公共 Releases API，串行请求发布列表，筛选 `v*` 标签、非 draft、非 prerelease 的条目。新仓库只承载这一应用，正式标签采用 `v0.5.0` 这样的标准形式；仍校验发布元数据中的应用身份，防止误包。公开发布信息可匿名读取，不要求用户填写 GitHub Token。[GitHub Releases API](https://docs.github.com/en/rest/releases/releases#list-releases)

每个 Hook 发布必须包含 `hook-update.json` 与固定命名的 APK；以下是**拟定协议示例，不是已存在的发布资产**：

~~~json
{
  "schemaVersion": 1,
  "applicationId": "com.yefeng.majmax.hookprobe",
  "channel": "stable",
  "versionCode": 8,
  "versionName": "0.5.0",
  "minSdk": 29,
  "abis": ["arm64-v8a"],
  "releaseTag": "v0.5.0",
  "assetName": "MajsoulMax-Hook-0.5.0-arm64-v8a.apk"
}
~~~

- 上例包名沿用原型，仅用于说明协议；最终 applicationId 由新应用发布配置确定，并由 CI 自动写入。
- CI 从最终 APK 提取包名、版本、最低系统与 ABI 生成元数据，不维护第二份手填版本号。元数据需与发布标签及确实存在的 APK asset 一致。
- `versionCode` 是升级排序依据；`versionName` 只展示，不能用字符串大小或发布时间决定升级关系。
- 当前版本取本机 PackageManager；渠道与构建类型由构建配置提供。版本 8 / 0.5.0 只是下一版示例，实施前分配实际未使用的版本号。
- 顺着 API 的 Link 分页遍历，首版最多读取 5 页、每页 100 项。超过上限仍有后续页时显示“无法确认最新版本”，不输出假定的最新结论；后续发布量增长再改为独立渠道索引。
- 合格发布中选择兼容的最大 versionCode；更高但不兼容的发布单独提示。所有 Hook 候选元数据必须完成检查，相关条目损坏或缺失时不能以较旧条目宣称已是最新。
- 返回 URL 经解析验证协议、主机与仓库身份；发布页使用该 release 的 `html_url`，元数据使用对应 asset URL。限制重定向到 GitHub 官方 API/资产域，未知目的地报错，不能执行任意远端地址。

### 6.2 网络行为

检查只由用户触发，重复点击复用同一个任务。连接超时 10 秒，单请求总超时 20 秒，整次检查预算 60 秒；JSON 体积上限 2 MiB、单个 Hook 元数据上限 64 KiB、更新说明展示上限 32 KiB。超出预算保留已知结果但标注检查未完成。

缓存 ETag 和已验证响应，304 使用对应缓存；没有缓存时不能把 304 当作空列表。403/429 检查限流头，遵守 Retry-After 或重置时间；其他权限错误另行提示。没有限流恢复时间时至少等待一分钟，首版不自动重试循环。[GitHub REST API 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

缓存只帮助展示历史结果，离线不能变成“已是最新”。更新错误写入管理应用日志，HTTP 响应体和凭据不直接落日志。

### 6.3 发布与签名

在新仓库新增专门的 `build-hook.yml`，触发 `v*` 标签和手动构建，完成原生库、APK、元数据与校验和的发布。版本、签名密钥、发布权限和 release 资产均由新仓库独立管理，不从旧应用的 CI 或签名环境自动继承。

Hook 发布要使用持续稳定的签名。当前本地安装产物为 debug 构建；正式签名若与已安装证书不一致，不能承诺覆盖安装。实现前读取现有 APK 证书与拟发布签名做比对，明确升级路径，不能靠重命名 APK 解决。UI 标明构建类型；CI 校验最终 APK 身份及证书，避免错包发布。

首版只打开发布页，因此不申请 REQUEST_INSTALL_PACKAGES。未来如增加应用内下载，再设计包名、versionCode、ABI、SHA-256、签名验证及系统安装确认；校验和不能替代签名身份检查。

以 `hook-probe` 为起点添加 Kotlin、Compose 与 Material 3，再迁移到新仓库作为独立 Android 工程。可沿用当前仓库已经验证的工具链版本，但新仓库必须有自己的 Gradle wrapper、版本目录和构建配置，不能引用旧工程的 `app/`。现有 Java API 102 入口保持独立，不能在游戏进程引用管理界面的 Compose 或 Application 初始化逻辑。

当前原型中的建议落点如下；这是迁移前的路径说明，不表示在旧代理 `app/` 中开发新界面：

### 新仓库交付边界

新仓库建议包含独立 Android 模块 `app/`、`native/`、`rust-modder/`、固定提交的 `external/MajsoulMax-rs/`、`docs/`、Gradle wrapper 和自己的 CI。这里的新 `app/` 指 Hook 应用模块，与本仓库现有同名目录没有依赖关系。

迁移时需要调整原生构建脚本、Rust `include!` 的相对路径、上游资源打包路径和子模块配置。保留上游固定提交、许可与归属说明；全新克隆并拉取子模块后即可构建，不能依赖原工作区的绝对路径、未提交文件或旧应用生成物。版本目录只携带新应用实际需要的依赖。

新应用可以与旧代理应用同时安装，各自拥有桌面入口与管理数据。首版不自动导入旧代理配置；已有游戏侧 MOD 配置由模块自身保留。原型 Hook 与正式 Hook 若更换了包名，迁移说明必须要求停用原型模块，避免同一游戏进程加载两份 Hook。

| 声明／能力 | 用途与边界 |
| --- | --- |
| INTERNET | 用户手动检查 GitHub 更新 |
| 目标游戏包 queries | 展示安装版本、获取启动 Intent |
| exported Launcher Activity | 提供桌面入口，外部 Intent 不能触发 root 命令或文件操作 |
| 非 exported FileProvider | 仅导出缓存目录，使用临时读取授权 |
| 设备 root 管理器授权 | 用户主动开启诊断读取时请求；不是 Android 普通运行时权限 |

首版不需要广泛存储权限、READ_LOGS、悬浮窗、无障碍服务、通知权限、VPN 服务或后台保活。关于页展示第三方库与上游许可，复用代码时保留其许可要求。

每个阶段完成后提交可检查的界面或证据；此处不预设已经通过验收。

| --- | --- | --- |

| P4 综合回归 | 升级、游戏设置页、性能、无障碍与生命周期 | 通过下列关键场景，记录 APK 版本和真机证据 |

### 必须覆盖的场景

1. 新应用首次安装、同身份覆盖安装、从 Launcher 与 LSPosed 打开、与旧代理应用共存；没有游戏、没有 root、拒绝或撤销 root 时管理界面仍可使用。若采用新 applicationId，还需验证原型模块停用后的独立启用流程。
2. 游戏正常初始化、原生库加载失败、Rust 配置失败、发送或接收 Hook 失败、仅 UI 注入失败；各阶段状态准确，模块失败仍按现有策略放行。
3. 游戏重启、应用重启、设备重启、系统时间改变、旧诊断文件残留；会话不混淆，不把历史成功当作当前启用。
4. 连续生成至少 10,000 条日志，验证队列与磁盘上限；轮转恰逢读取、末行半写、非法 JSON、超长行、磁盘满、读取进程超时均不使游戏或界面卡死。
5. 日志筛选、搜索、暂停、返回最新、旋转屏幕、切后台再返回、复制与两种导出范围；共享结果与界面选择一致且无敏感字段。
6. 更新结果涵盖相同、较新、较旧版本，`0.9` 与 `0.10` 显示名，代理版、上游版、预发布、缺少 metadata、错误包名、ABI/minSdk 不符、重复版本码及损坏字段。
7. 更新源未配置、切换到新仓库构建、分页、304 有／无缓存、断网、超时、403/429、非限流权限错误、重定向异常、返回 HTML；均不会请求旧仓库或错误显示“已是最新”。缓存按 owner/repo/channel/applicationId 分区，换源不能复用旧结论。
8. 图标各蒙版、浅深色、320 dp 窄屏、横屏、字体放大至 200%、系统栏与键盘、TalkBack 标签；日志文字与操作保持可读可点。
9. 安装更新后进入游戏，回归 MOD 设置六个开关、昵称确认、“恢复原昵称”及普通礼品码弹窗；管理界面不改变配置保存与消息处理行为。

自动化验证优先覆盖日志解析／轮转去重、状态归并和更新筛选这些逻辑；界面布局与 root/LSPosed 集成以真机验证为准，不为静态文案编写重复实现的测试。

## 9. 实现前仍需实证的事项

- 当前设备 root 管理器对管理应用只读目标文件的实际授权、SELinux 行为及超时处理，需要 P0 真机验证。
- 新仓库地址待用户提供；通过构建配置定向即可。地址未配置时显示“尚未配置更新源”，配置后尚无合格发布资产时显示“暂未找到发布包”。当前不创建新仓库、不上传代码，也不修改旧仓库的 release。
- 新仓库需要建立与本协议配套的 Hook CI；本方案未认定远端已存在 `hook-update.json`。
- 正式签名与当前本地 debug 签名的兼容性尚未比对；这一点影响覆盖安装路径，不影响先实现三页界面。
- 当前模块日志没有稳定事件协议；需要补充结构化事件后才能实现可靠的状态与筛选，不能只通过翻译现有字符串拼接出“已生效”。

设计完成标准：用户能安装独立发布的新应用，从新图标打开模块管理界面，看懂最近运行证据、定位并导出日志、准确检查新仓库中的 Hook 版本更新；游戏内 MOD 配置继续使用已经完成的游戏原生界面。
